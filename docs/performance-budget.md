# Performance budget 1 / 2 / 4 / 8

## Назначение

Performance budget защищает основной пользовательский сценарий: специалист редактирует заголовок уже подготовленного лёгкого макета, а генератор обновляет все печатные копии. Проверка не является микробенчмарком отдельной функции — она запускает реальный `index.html` в системном headless Chrome и работает через те же DOM-события, что и пользователь.

## Сценарий

Для 1 / 2 / 4 / 8 копий runner отключает тяжёлые фото, QR и отрывные полосы, выполняет 2 warm-up изменения, затем 7 измеряемых изменений заголовка. Для каждой серии сохраняются samples, median, worst sample и median синхронной части dispatch/render. После совпадения текста во всех `.flyer` runner ждёт два `requestAnimationFrame` и проверяет, что mutations печатного листа прекращаются.

Перед измерениями runner ждёт полной загрузки библиотеки шаблонов и дополнительное окно стабилизации. Это повторяет доказанный `form-input-render-smoke` и исключает гонку с первоначальным `init()`/применением шаблона.

## Baseline

Baseline записан 9 августа 2026 года на системном Chrome GitHub Actions (`ubuntu-24.04`) в run `31325937276`, head `6f54543f7ff659e02add5b16888bfd52d4e90709`.

| Копий | Median | Worst | DOM nodes | Fixed ceiling |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 33.2 ms | 40.9 ms | 16 | 120 ms |
| 2 | 33.1 ms | 42.6 ms | 32 | 140 ms |
| 4 | 33.0 ms | 33.3 ms | 64 | 180 ms |
| 8 | 32.9 ms | 34.0 ms | 128 | 240 ms |

Предварительные ceilings `250 / 300 / 450 / 700 ms` использовались только до получения реального Chrome-baseline. После baseline они один раз ужесточены до `120 / 140 / 180 / 240 ms`: это оставляет многократный запас относительно фактической median и worst, но уже ловит заметное многократное замедление вместо почти неограниченного роста.

DOM в baseline растёт строго линейно: `16 → 32 → 64 → 128`.

## Scaling guard

Граница 4 → 8 дополнительно проверяется независимо от абсолютных ceilings:

`median(8) <= median(4) × 3 + 50 ms`.

Baseline: `32.9 <= 33.0 × 3 + 50`. Правило намеренно широкое: оно ловит явный сверхлинейный рост, но не превращает шум GitHub runner в release blocker.

## Structural guards

Runner проверяет точное количество `.flyer`, обновление заголовка во всех копиях, линейно ограниченный рост DOM относительно одной копии и прекращение mutation callbacks после окна стабилизации. Один единичный выброс не проваливает build, если median в бюджете и worst sample не выглядит как экстремальное зависание.

## Flaky CI

Budget не повышается из-за единичного красного run. Инфраструктурный/CDP сбой допускает один внутренний повтор benchmark. Старые smoke могут отдельно иметь инфраструктурный/фокусный флейк; такой rerun не считается основанием менять performance ceilings. Настоящее превышение median или structural/scaling guard не маскируется повторными запусками.

## Когда менять budget

Budget нельзя автоматически повышать после красного CI. Сначала нужно отличить инфраструктурный/CDP сбой от настоящего regression, посмотреть samples, median, worst, DOM и scaling. Изменение fixed ceilings после этого PR допускается только отдельным обоснованным изменением с новым подтверждённым baseline и без ослабления функциональных guards.
